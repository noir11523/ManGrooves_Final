# ManGROOVES relational database

The migration creates 24 tables under the PostgreSQL schema `mangrooves` and 33 foreign keys, including the link to Supabase Auth. In the Supabase schema visualizer, select **mangrooves** after the migration. The website and app continue using their existing API and account IDs. [Physical ERD](diagrams/MANGROOVES_RELATIONAL_ERD.svg)

| Records | Where they live |
| --- | --- |
| Identity and location | `actors` links a local contributor ID to an Auth UUID. `users`, `expert_applications`, `barangay_keys`, and `barangays` hold profiles, applications and locations. Historical reports retain the contributor ID after an account is deleted. |
| Field reporting | `reports` references users, sites, species and follow-up reports. `report_extra_photos` keeps additional photo paths in order. `clusters` stores sites. The private objects keep their original paths in Storage. |
| Species and checklist | `species`, `criteria`, and `checklist_choices` store species, questions and ordered answers. Submitted observations and traits remain snapshots so editing the checklist does not rewrite history. |
| Review and recognition | `verification_logs`, `audit_logs`, `notifications`, `notification_keys`, `badges`, `user_badges`, and `certificate_links` keep the review, notification and award records. |
| Operations | `photo_claims` tracks photo reuse. `rate_limits`, `migration_files`, and `meta` retain service state. `record_types` maps the API collections to SQL tables. `legacy_missing_references` records an old ID whose target was already missing at migration. |

Application tables keep the existing document key and revision. Typed columns hold regular fields. JSONB preserves historical answer snapshots, versioned configuration such as custom trait catalogs, and older fields or representations required by existing clients. A compatibility view reconstructs the old API format. The original document table stays in the private archive schema. PostGIS continues to use the existing barangay boundary table and spatial index.

## Restore rehearsal and production switch

1. Keep the existing project and source. On the Windows workstation run `node supabase/scripts/backup-workspace.js` for an encrypted archive of the whole folder, including Git and ignored configuration. Verify it with `node supabase/scripts/backup-workspace.js verify BACKUP_FOLDER`. To unpack into a new empty directory, use `restore BACKUP_FOLDER EMPTY_DIRECTORY`. Keep an independently recoverable copy of deployment configuration, Auth provider settings, email credentials and Android signing material in an approved secret store.
2. Run `node supabase/scripts/backup-storage.js` with the existing Supabase CLI login. This saves both buckets, paths, content types, settings, sizes and checksums under the Windows user's Local AppData. Reopen the archive with `node supabase/scripts/restore-storage.js BACKUP_FOLDER`. These encrypted backups require the Windows user's DPAPI credentials. Establish separate recovery access before relying on them off-device.
3. Restore the selected physical database backup to a **new Supabase project**. Record the target reference and backup UTC timestamp. Isolate outbound email, scheduled jobs, webhooks and integrations from production recipients. Use disposable test accounts for write tests. Compare Auth UUIDs, linked identities and profile roles in the clone with the evidence for the backup date. Check sign-in and recovery with controlled accounts. Allow for accounts or records created after the backup date when comparing with the live project.
4. Recover the separately backed-up objects into the confirmed clone with `node supabase/scripts/restore-storage.js BACKUP_FOLDER --to-clone CLONE_REF`. The tool refuses the live source and downloads each target object to check its checksum. A physical clone can already contain an object's catalog row while its file is missing. The tool checks that the catalog ID matches and rechecks that the file is missing before restoring its bytes. A readable file with different contents stops the restore. Test private report photos and ID access through the app. Check references at the database backup date against the file backup date.
5. Run `node supabase/scripts/rehearse-relational.js CLONE_REF` to test the clone's source data in local PostgreSQL. Apply the relational migration **in the clone**. The SQL checks all record keys, values and revisions against the archived table in the same transaction. Review any rows in `mangrooves.legacy_missing_references`. The API preserves the historical value while its unresolved SQL foreign key stays null. New broken references fail.
6. Point a staging web build and Android build to the clone. Test all three roles, sign-in, location coverage, the four-step report, mixed valid and invalid uploads, duplicates, expert correction, site updates, analytics, timeline, notices, awards, export and audit. Compare selected API responses, counts and permission results against the baseline. Test the rollback on the clone, including a report edited after migration.
7. After these checks pass, schedule a short write pause. Capture fresh database and Storage backups for cutover, verify the external files and compare the latest record counts. Apply the reviewed SQL to production within its transaction. Recheck Auth, data parity, private photos and critical workflows before enabling writes and publishing client updates. Keep the archive and backups through the acceptance period.
8. If the migration transaction fails, PostgreSQL rolls it back. If a later check fails, pause writers and run the separately tested `supabase/manual-migrations/rollback-relational.sql`. It rebuilds the document table from the *current* relational records, preserving edits, new records and deletions since cutover. It retains the pre-migration archive and relational schema for investigation. Keep cloud Storage in place. A physical backup restore is a separate disaster-recovery operation and requires reconciling writes after its timestamp.

## Report photo checks

Each newly selected photo is checked independently. Accepted photos stay attached when another fails. The website and Flutter app clear the old warning when a new selection starts and dismiss batch feedback after eight seconds. The API checks all report photos again before saving. Required overview and close-up photos, ten photos total, private storage and duplicate detection still apply.

The shared limits are in `supabase/functions/api/core/photo-quality-config.json`. Keep `mobile/flutter_app/assets/config/photo_quality.json` in sync. The default minimum is 800 pixels on the shorter side. The API accepts JPG, PNG and WebP up to 5 MiB each, 12 MiB combined, and 6 megapixels per image presented for server processing. Brightness and contrast checks measure exposure. Local sharpness lets a focused close-up pass with a soft background. Directional edge measurements help reject camera shake and light trails. These are clarity checks. An expert determines the meaning of the photos.
